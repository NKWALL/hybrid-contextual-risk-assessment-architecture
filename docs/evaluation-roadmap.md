## 1. 為什麼要做這件事

目前系統無法回答一個根本問題：

> **「你的系統判斷得準不準？」**

現有的單元測試（目前 88 條）證明的是「程式沒寫錯」，不是「風險判斷是對的」。沒有任何東西可以量化系統的判斷品質。

因此整條路線的目標只有一個：

> **造出一份可信的「參考答案」，用它來量測系統。**

### 為什麼不能自己標一份答案就好

可以標，但會被質疑「自己出題自己改」。因此需要證明這份答案**不是一個人說了算**——找多個獨立標註者（多個 LLM + 作者 + 組員）各自獨立標註，再用 **Kappa** 計算一致程度。

Kappa 高 → 「多個獨立標註者對這批答案有共識，因此可信」→ 用它算出來的準確度才有意義。

**B5 不是在評估系統，是在造一把可信的尺。** 評估系統是 B6 的事。

## 2. 三個資料集與各自的紀律

案例池共 **54 則**，位於 `python_backend/evaluation/case_pool.json`。

| 集合 | 數量 | 用途 | 紀律 |
|---|---|---|---|
| **dev** | **21** | 調參專用：跑系統、看軌跡、找錯、修正 | 可反覆使用。**不要追求 100% 命中**（會過擬合） |
| **test** | **22** | 主測試集：baseline、調參後、加入覆審後的對照 | **事先宣告測量次數**；所有調校依據一律來自 dev；**測完不因分數不滿意而回頭改** |
| **holdout** | **11** | 最終封存：全程不測量、不檢視 | 所有調校與功能開發完成後，**開封測一次**，作為未受重複測量影響的最終數字 |

> **參考答案有兩版**（`ground_truth.json`）：`gt_adjudicated`（裁決者版）與 `gt_majority`（多數決版）。
> 因裁決者同時為系統設計者，須**對兩版各計算一次指標**作為敏感度分析。詳見 `current-specs/annotation-adjudication.md` §2。

### 什麼算「洩題」

| ✅ 可以 | ❌ 不行 |
|---|---|
| 幫 test/holdout 標答案（標註者看的是對話，系統沒參與） | 看系統在 test 上**哪幾題錯**，針對那幾題調參數 |
| 跑 test 看**總分** | 反覆測十幾次、挑分數最好的那一版（適應性過擬合） |
| 修改依據來自 **dev** | 修改依據來自 **test 的失敗案例** |

**核心判準：洩漏的不是「跑了 test」，是「用 test 的結果去決定怎麼改系統」。**

### 一個容易混淆的點

**標註 ≠ 調參。** 標註階段標註者只看「對話內容」產出「答案」，系統完全沒參與、參數完全沒動，因此不構成污染。這就像出題老師寫解答本——老師知道答案不是作弊，考生偷看考卷才是。

`holdout` 封存的是「**測量時機**」，不是「標註時機」——它現在就要和 test 一起標好答案，只是標完鎖起來不看。

## 3. 完整流程（七步）

```
【B5 造尺】✅ 第一輪已完成；第二輪重做
  ① 造案例 ──→ ② 多方標註 ──→ ③ 算 Kappa ＋ 裁決 ──→ ③b 分層切分並鎖定

【B6 量測與校準】⬅ 現在在這
  ④ 量系統(baseline) ──→ ⑤ 用 dev 調參再量

【加分項】
  ⑥ 加入 LLM-as-judge 覆審再量 ──→ ⑦ 開封 holdout
```

| 步驟 | 內容 | 對應里程碑 | 狀態 |
|---|---|---|---|
| ① | 造案例（第一輪 54 則；**第二輪：造完先不切分**） | B5a | ✅ |
| ② | 多方標註（3 LLM + 作者） | B5b | ✅ |
| ③ | 算 Kappa + 裁決不一致案例 | B5c | ✅ |
| ③b | **分層切分三份並鎖定**（第二輪新增，見 ③b） | — | ⬜ |
| ④ | **量系統 baseline** | B6a | ⬅ **下一步** |
| ⑤ | 用 dev 調參 → 再量 test | B4a/b、B6d/e | ⬜ |
| ⑥ | **加入非同步強模型覆審 → 再量 test** | （研究貢獻） | ⬜ 加分項 |
| ⑦ | 開封 holdout，測一次 | — | ⬜ |

> ⑥ 的設計與測量順序見 **§4**。若時間不足，⑥ 可只寫入研究計劃的未來工作，直接由 ⑤ 進到 ⑦。

### ① 造案例 🔄 **第一輪已完成並退役，第二輪重造中**

每則案例 = **一段對話歷史 + 一則要判斷的目標訊息 + 關係階段等 meta**。

**為什麼是「一段對話」而不是「單句」**：本系統的核心是累積狀態與情境判斷。同一句「你在哪」，在約見面時是 `safe`、在反覆逼問行蹤時是 `warning`。若只標單句，等於在測一個退化成單句分類器的系統，測不到最有價值的部分。

第一輪案例池含五類（當時是造完即分層切分；**第二輪改為標註、裁決後再切分**，見 ③b）：

| 類別 | 數量 | 用意 |
|---|---|---|
| 低風險／正常互動 | 10 | 確認不誤報 |
| 中風險（各維度升溫） | 12 | 涵蓋五個風險維度 |
| 高風險（明確越界／威脅） | 10 | 確認抓得到 |
| **脈絡對照組**（同句不同前文，5 對） | 10 | **證明累積狀態與情境判斷有效** |
| **誤擋回歸**（敏感詞在求助／新聞情境） | 8 | 確認禁詞二元化生效、不誤攔 |
| **深夜時段** | 4 | 涵蓋 3 條時段情境規則，含 1 則「深夜但正常」對照 |

### ② 多方標註 🔄 **第一輪已完成，第二輪須重標（含 dev）**

對 **test 22 + holdout 11 = 33 則**，由多個標註者各自**獨立**標註（互不可見）：

- **三個 LLM**：`qwen3.5:397b`／`glm-5.2`／`gpt-oss:120b`（Ollama Cloud，不同廠系）各標一次
- **作者本人**標一份
- **組員**：尚未進行，建議補做以解決「唯一人類標註者即系統設計者」的限制

標註內容（詳見 `docs/current-specs/annotation-rubric.md`）：

| 標籤 | 內容 | 用途 |
|---|---|---|
| **主要：風險等級** | safe / observation / warning / restricted / blocked | **Kappa 主指標**，對齊系統實際決策 |
| **輔助：是否介入** | 是／否 | **不手標**，由五級自動換算。穩健備援指標 |
| **質性：主要風險維度** | 五維度之一或 none | **不進 Kappa**，供事後分析各維度強弱 |

> **為何不標「五個維度各幾分」**：本規模的案例數撐不起 5×5 的細粒度一致性，Kappa 會失去意義。標籤粒度需與樣本數相稱。

### ③ 算 Kappa 🔄 **第一輪已完成，第二輪須重算**

- 多個 LLM 之間 → **Fleiss' Kappa**
- 作者 vs LLM 共識 → **Cohen's Kappa**
- 五級為有序尺度 → 主指標用 **quadratic-weighted Kappa**

**Kappa 的意義**：扣掉「純靠各自標註習慣碰巧一致」的部分後，真正的共識有多少。公式精神為 `(實際一致率 − 巧合一致率) / (1 − 巧合一致率)`。

**低 Kappa 不是失敗**：代表準則有模糊處（→ 修訂準則後重標）或案例本質具爭議（→ 保留並討論）。分歧案例本身就是「連人與 AI 都難判定之邊界情境」的研究素材。

**實際結果**：Fleiss' Kappa **0.682**（五級，substantial）／**0.899**（是否介入，almost perfect）；人 × LLM 加權 Cohen **0.897–0.913**。33 則中 12 則有分歧，已逐案裁決並記錄（`current-specs/annotation-adjudication.md`）。

⚠️ **不得宣稱「三個 LLM 高度一致 ＝ 多方獨立驗證」**：不同廠商的 LLM 訓練語料重疊、對齊方式相近，其共識部分來自共同先驗。準則清晰度的證據應以**人 × LLM**（0.897–0.913）為準。

### ③b 分層切分並鎖定 🆕 **第二輪新增：切分在裁決之後、測量之前**

第一輪是造完案例就切分，切分時只有設計者的 `intended` 可用，結果 test／holdout 的 `observation` 樣本數為 0。
`intended` 相對裁決版**系統性偏低**（`case-pool-design.md` §1.4），用它分層會分錯。
標註不構成洩題（見 §2「一個容易混淆的點」），所以第二輪把切分往後移：

1. **先全部標註、算 Kappa、裁決分歧**——三件事都在任何系統跑之前做完（裁決時若已看過系統在哪幾題錯，會不自覺往系統靠）
2. **切分單位是整段對話**：一段對話的所有標註點落在同一個 split（`case-pool-design.md` §1.2）
3. **分層鍵**：對話的裁決版等級組成（至少依「該段最高等級」分層）＋ `covers[]` 機制編號
4. **每個 split 五級都要有樣本**，`observation` 尤其要檢查；某個機制若只有一段對話覆蓋，放 dev
5. 用固定隨機種子執行、把切分結果與種子寫進 `case_pool.json`，**之後不再改動**

切分完成才進 ④。

**B5 至此完成。**

### ④ 量系統 baseline（B6a）

將 **test 22 則**餵進完整 pipeline 跑一遍，比對參考答案，計算 precision / recall / F1 等指標（第二輪的指標定義與判定規則見 **§7**）。這是第一次能用數字回答「系統多準」。

**這一步需要整套系統跑起來**（MySQL + Appwrite + Gemini API + Ollama 的 guardrail 與背景判斷模型），不只是 LLM。

⚠️ **執行前務必確認本機 Ollama 已啟動且已下載 `llama-guard3:1b` 與 `gemma4:e2b`**。否則測到的 baseline 是「少了兩層 Guardrail 的系統」，該數字不能代表完整設計，之後的對照組也會失準。

### ⑤ 用 dev 調參 → 再量 test（B4a/b + B6d/e）

1. 用 **dev 21 則**跑系統、讀後台軌跡、定位錯誤 → 調 `kb_features` 數值、prompt 措辭、五等級閾值
2. 調完再跑 **test 22 則** → 得到「調參後」分數
3. **前後對照 = 校準有效的證據**

此步同時解鎖先前卡住的 **B4a（調特徵表）與 B4b（調 prompt）**——它們之前無法進行，正是因為缺少 dev 案例作為依據，只能憑感覺調整。

調校時的規範詳見 `docs/current-specs/tuning-protocol.md`。

### ⑥ 加入 LLM-as-judge 覆審 → 再量 test（加分項）

即時判斷維持輕量模型以確保低延遲；另在背景以固定週期呼叫推理能力較強的模型，回頭覆審這段期間的判斷是否有誤。

**這是本專題最具研究深度的一步**，對應 `known-issues.md` P0#3（LLM 自評信心不可靠），亦為研究計劃的核心主張。

設計與測量順序見 **§4**。若時間不足可略過，直接由 ⑤ 進到 ⑦。

### ⑦ 開封 holdout（只測一次）

所有調校與功能開發完成後，開封 11 則封存案例測一次。此為**未受重複測量影響**的最終效能數字。

⚠️ **若執行 ⑥，⑦ 必須延後至覆審評估之後**——holdout 只能測一次，要留給最終版本。

## 4. ⑥ 的設計細節：非同步強模型覆審

完成上述基礎建設後，才能做最有價值的驗證：

對應 §3 的步驟 ④⑤⑥⑦，展開成測量順序（此處用「測量 N」標記，避免與 §3 的步驟編號混淆）：

```
測量 1  ← §3 步驟④   test：未調參、無覆審        （baseline）
        ← §3 步驟⑤   用 dev 調參
測量 2  ← §3 步驟⑤   test：已調參、無覆審        ← 覆審的「之前」
        ← §3 步驟⑥   加入非同步強模型批次覆審
測量 3  ← §3 步驟⑥   test：已調參、有覆審        ← 覆審的「之後」
測量 4  ← §3 步驟⑦   holdout：最終數字（只測一次）
```

**測量 2 與測量 3 必須成對比較**：兩者都是「已調參」的系統，唯一差別是有無覆審，差值才能乾淨地歸因於覆審。若拿測量 1 與測量 3 相比，差值同時包含調參與覆審兩件事，無法分離。

該差值即是「輕量模型即時判斷 + 背景強模型批次覆審，能否在不增加即時延遲下提升準確度」的答案。

**順序不可顛倒**：若在建立 baseline 之前就加入覆審，將永遠無法量化其效益，只剩「做了一個功能」。

> **優先序**：覆審（§3 步驟 ⑥）是**加分項**。若時間不足，可只寫入研究計劃的未來工作，直接由 ⑤ 進到 ⑦。

設計細節見 `docs/integration-review-20260729.md` §7.2。

| **有餘裕** | LLM-as-judge 覆審（此時 holdout 須延後至覆審評估之後） |

⚠️ **執行任何量測之前必須確認**：本機 Ollama 已啟動且已下載 `llama-guard3:1b` 與 `gemma4:e2b`。
否則測到的是「少了兩層 Guardrail 的系統」，該數字不代表完整設計。

**優先序**：judge 是加分項。專題完整性取決於「改腳本 → 造案例 → 標註 → 量測 → 報告」這條線走完。

## 6. 五個技術注意事項（評估腳本必須處理）

1. **時間戳整體平移「整數天」**：使目標訊息對齊執行當日的**同一時刻**，同時保留相對間隔與時段語意。若不平移，系統會以為訊息是數週前發送，行為特徵（連發次數、頻率、間隔）全部失真、規則引擎不觸發，baseline 偏低。

2. **呼叫 `/detect` 時帶入 `message_timestamp`**：使深夜等時段規則以**訊息時間**而非執行時間判定，結果才可重現。

3. **每案獨立 conversation_id**：系統具備跨訊息的累積狀態。若多個案例共用同一對話，前一案的風險會累積到下一案。

4. **關係背景要「種資料」，不可偽造訊息**：
   - 案例的 `meta.relationship_facts`（累積訊息數、互動天數、對話平衡度）與 `meta.seed_metrics`（`familiarity_score`、`intimacy_level`、`intimacy_progression_rate`）需**於執行前寫入 Appwrite 的 `relationship_metrics` 與 `conversation_summaries`**。
   - 系統會照常從自己的資料庫讀取，行為與正式運作完全一致。
   - ⚠️ **絕不可為了湊出 `total_messages` 而產生假訊息**：`messages` collection 只應寫入該案例自身的 `context_messages`。否則系統會讀到標註者看不到的歷史，造成資訊不對稱，評估結果失去意義。
   - 不種資料的後果：案例標示「熟識」，但系統看到的是一個只有 5 則訊息的全新對話，會算出「剛認識」。標註者與系統將在判斷**不同的情境**，且 3 條依賴關係指標的情境規則永遠不會觸發。

5. **每案跑完後清除該對話的資料**，避免殘留影響重跑。

## 7. 評估指標與計算方式（第二輪）

> 本節把「量什麼、怎麼算、怎麼判定有沒有變好」在測量之前寫死。測量 1–4 全部沿用同一套，
> 不得在看到分數後增減指標或改判定規則。現行 `evaluation/metrics.py` 已實作其中大部分，缺口列於 §7.6。

### 7.0 分析單位與比對方式

| 項目 | 規定 |
|---|---|
| 樣本 | **一個標註點 ＝ 一個樣本**。一段對話 3 個標註點 ＝ 3 個樣本；切分單位仍是整段對話（`case-pool-design.md` §1.2） |
| 系統答案 | 該標註點的訊息經 `/detect` 後回傳的 `risk_level`。**以等級為準，不以「卡片有沒有顯示」為準**——節流與已處置豁免會抑制顯示但不改等級，那些機制由涵蓋檢核表 D3／E 系列另測 |
| 參考答案 | 兩版各算一次：`gt_adjudicated`（主）、`gt_majority`（敏感度分析） |
| 介入門檻 | `warning` 起算為「介入」（`metrics.py` 的 `INTERVENE_FROM`）。`observation` 不算介入——它對寄件方不顯示任何東西 |
| 等級距離 | safe 0 → observation 1 → warning 2 → restricted 3 → blocked 4 |

### 7.1 A 層：介不介入（二元）

把五級折成兩類：參考 ≥ warning 為「該介入」，系統 ≥ warning 為「有介入」。

| | 系統：介入 | 系統：不介入 |
|---|---|---|
| **參考：該介入** | TP | FN（漏報） |
| **參考：不該介入** | FP（誤報） | TN |

| 指標 | 公式 | 回答什麼 |
|---|---|---|
| **Recall** | TP／(TP＋FN) | 該介入的抓到幾成。＝ 1 − 漏報率 FNR |
| **FPR（誤報率）** | FP／(FP＋TN) | 不該介入的被誤抓幾成 |
| Precision | TP／(TP＋FP) | 系統出手時幾成是對的 |
| F1 | 2PR／(P＋R) | 兩者的調和平均 |

- ⚠️ **FPR ≠ 1 − Precision**（分母不同）。真實流量中不該介入者佔絕大多數，FPR 很小時 precision 仍可能很低，兩個都要報。
- ⚠️ 分母為 0 時（例如系統整輪從未介入）寫 **n/a**，不寫 0.0。

### 7.2 B 層：五級等級（有序）

先列 **5×5 混淆矩陣**（列＝參考、欄＝系統），B 層所有指標都由它算出。

| 指標 | 算法 | 角色 |
|---|---|---|
| **Quadratic-weighted κ** | 權重 w(i,j)＝(i−j)²／16；κ＝1 − Σw·觀察比例 ／ Σw·期望比例（期望＝兩邊邊際分佈相乘）。差 1 級罰 1/16、差 2 級罰 4/16、差 4 級罰 1 | **主指標**。與標註者間一致性（人 × LLM 0.897–0.913）同一算法，可並排 |
| 未加權 κ | 同上，w 為 0／1 | 參考。與加權版落差大 ＝ 錯誤多為差一級 |
| Adjacent ±1 | 對角線＋相鄰兩條斜線 ／ n | 差一級以內的比例 |
| MAE（級） | Σ｜系統 − 參考｜／ n | 平均差幾級 |
| Accuracy | 對角線 ／ n | **只當參考**。類別不平衡下無意義 |
| 每級 P／R／F1 | 該級當正類、其餘當負類，一級算一次；TP＝對角格、FN＝該列其餘、FP＝該欄其餘 | 找出哪一級弱 |
| Macro-F1 | 參考答案中**有出現**的等級之 F1 取平均 | 不讓多數級蓋掉少數級 |
| 反應過度率／不足率 | 系統＞參考的格數／n；系統＜參考的格數／n | 錯的方向 |
| **災難漏報** | 參考 ∈ {restricted, blocked} 且系統 ∈ {safe, observation} | **逐則列出案例編號**，目標 0 |
| 錯鎖 | 參考 ∈ {safe, observation} 且系統 ∈ {restricted, blocked} | 逐則列出，目標 0 |

### 7.3 序列專屬：介入時機

第一輪測不到累積，第二輪用這一項補。只對「參考答案在某個標註點起 ≥ warning」的對話計算：

- 令 p 為參考**首次** ≥ warning 的標註點，其訊息索引為 m_p；p−1 為前一個標註點，索引 m_{p−1}（沒有前一點則取 0）
- 令 m_s 為系統**首次**輸出 ≥ warning 的訊息索引（系統每則都有輸出）
- 判定：

| 結果 | 條件 | 說明 |
|---|---|---|
| 準時 | m_{p−1} < m_s ≤ m_p | 在標註者認可的區間內介入 |
| 晚 | m_s > m_p | 延遲 ＝ m_s − m_p 則 |
| 早 | m_s ≤ m_{p−1} | 同時是前一標註點的誤報，已計入 7.1 |
| 未介入 | 整段都未到 warning | 同時是漏報，已計入 7.1 |

報告準時／晚／早／未介入各幾段，「晚」的列出延遲則數。這是唯一直接量「累積判斷」的指標；
脈絡對照對（`contrast_pair_analysis`）繼續保留作為第二個證據。

### 7.4 主指標、護欄與「有沒有變好」的判定

在測量 1 之前定案，之後不改：

| 角色 | 指標 | 判定 |
|---|---|---|
| 主指標 | QWK（裁決版） | 調參後 > 調參前 |
| 護欄 1 | 介入 Recall | 不得下降 |
| 護欄 2 | FPR | 不得上升 |
| 護欄 3 | 災難漏報數 | 不得增加 |
| 敏感度 | 以上四項用多數決版重算 | 結論方向須一致；不一致要寫出來 |

**「變好」＝主指標上升且三條護欄都沒撞到。** 只有主指標上升、有護欄撞到 → 寫「以 X 為代價的改善」，不寫「改善」。

小樣本必附兩件事：

1. **一個樣本等於幾個百分點**（n＝24 → 約 4.2 pp）。差距小於兩個樣本者不宣稱方向。
2. **逐點配對表**：同一個標註點在調參前後各一個等級，數「變好／變差／不變」各幾點。
   同一份資料的配對比較，比兩個總數相減有說服力；檢定力的限制見 §5 的警語。

### 7.5 報告格式

- 主表：列＝指標（7.1 四項、7.2 的 κ／Adjacent／Macro-F1／災難漏報、7.3 準時率），欄＝測量 1／2／(3)／4，每格「裁決版／多數決版」。
- 附錄：每次測量的 5×5 矩陣、每級 P／R／F1 表、逐點結果表（含 7.4 的配對欄）、災難漏報與錯鎖逐則清單、涵蓋檢核表斷言通過表、NLP 主維度命中率。
- 第四層另表：P@10、AP、有害者名次表（完整／消融並列）、前 20 名誤傷清單（§7.7）。

### 7.6 腳本現況與缺口

`evaluation/metrics.py` 已有：QWK／未加權 κ、accuracy、adjacent、MAE、每級 P／R／F1、macro-F1（只算參考中出現的級）、
介入 P／R／F1／FPR／FNR（門檻 warning）、方向率、分層統計、脈絡對照對。

第二輪要補：

| 缺口 | 說明 |
|---|---|
| 混淆矩陣輸出 | 現只算指標不印矩陣；報告要印 |
| 災難漏報／錯鎖清單 | 新增，逐則列 case id |
| n/a 處理 | `prf()` 分母為 0 時回 0.0，應回 None 並在報告印 n/a |
| 配對比較 | 新增：讀兩份預測檔，逐點比對，輸出變好／變差／不變 |
| 介入時機（7.3） | 新增；前提是 `run_eval.py` 支援序列並保留每則的輸出（§5 步驟 0） |

**局部評分（語意層）**：NLP 主維度命中率——系統選反思文案用的最高維度 vs 標註 `primary_dimension`，
只算參考等級 ≥ observation 的點；需 `run_eval.py` 記錄該維度。進附錄，不進主表。
七層裡只有 NLP 與 Guardrail 分類器是會「判錯」的層，其餘是確定性算式，只有正確性（單元測試、
`case-pool-design.md` §2.8 的 trace 斷言）與消融貢獻（§7.7）可言；這一項是 NLP 唯一的獨立數字。

**不適用於等級輸出**：MAP、MRR、nDCG 等排序清單指標——標註點層級沒有「一個 query 回一串清單」的結構。
排序指標只用在 §7.7 的使用者層。

### 7.7 第四層：使用者排序＋消融（實驗二）

單位換成「人」、資料換成不平衡人群，用排序指標回答「有問題的人挑不挑得出來」與「累積有沒有貢獻」。
這是 selection（§7.1–7.3）之外的 ranking 視角，兩者互補：排序看不到等級對不對，等級評估看不到
真實比例下的誤傷量。資料規格見 `user-ranking-design.md`。

| 項目 | 規定 |
|---|---|
| 資料 | 10 有害（含 3–4 人慢速升溫：每則 `risk_delta_total` 最大維度 < B_WARNING、累積後跨級）＋ 100 安全（含 20–30 難負例），每人一段 10–14 則對話；人只標「有／沒問題」 |
| 時機 | 調參定案之後只跑一次；不進 dev；與案例池不重疊 |
| 排序鍵 | 整段最高 `risk_level`，同級內整段最高 `composite`（含覆寫）；平手依 max 維度、再依 id |
| 消融（零成本版） | 同一份 trace，改用單則 `risk_delta_total` 最大值排序＝沒有狀態累積的系統 |
| 消融（嚴格版，選做） | 每則重置 risk state 重跑（保留關係種資料），同一排序鍵 |
| 指標 | P@10、AP（10 個有害者為 relevant，簡報 IR p.38 的算法）；每個有害者的名次（完整 vs 消融並列）；前 20 名內的安全者清單與歸類 |
| 判定（測量前定案） | 不設及格線（一個正例＝10 pp）；**累積有貢獻** ＝ 完整版 AP ≥ 消融版 AP，且慢速升溫者在完整版的名次全部優於消融版 |
| 限制 | 零成本消融隔離的只是狀態累積（NLP 的前文視窗與情境層仍在）；9% 仍高於真實比例 |
